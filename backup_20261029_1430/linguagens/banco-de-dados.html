🏛️ Banco de Dados

Os bancos de dados relacionais são o alicerce fundamental de toda aplicação digital moderna. Desde a revolução teórica de Edgar F. Codd na IBM em 1970 até o nascimento de gigantes de código aberto como o MySQL (1995) e o PostgreSQL (1996), descubra como estruturar, proteger e escalar o ativo mais valioso de qualquer sistema: os dados.

História & Evolução dos SGBDs

Cinco décadas de engenharia de dados: de teorias matemáticas à nuvem global e bancos serverless.

1970

Modelo Relacional (Edgar F. Codd, IBM)

O cientista britânico Edgar F. Codd publica o lendário artigo "A Relational Model of Data for Large Shared Data Banks" no laboratório da IBM. Ele introduziu a álgebra relacional, separando a estrutura lógica dos dados do seu armazenamento físico em disco.

1974

SEQUEL / System R (IBM San Jose)

Donald Chamberlin e Raymond Boyce criam a linguagem SEQUEL (posteriormente renomeada para SQL) como interface declarativa para o projeto System R da IBM, provando a viabilidade de transações e otimização de consultas relacionais.

1979

Oracle V2 — Primeiro SGBD Comercial

Larry Ellison, Bob Miner e Ed Oates fundam a Relational Software Inc. (atual Oracle) e lançam a versão 2 do Oracle Database, o primeiro SGBD relacional comercial a implementar a linguagem SQL no mercado corporativo.

1983

IBM DB2 & Padronização Corporativa

A IBM lança oficialmente o DB2 para mainframes MVS. O banco estabelece padrões industriais para transações ACID pesadas, catalogação e auditoria em bancos e seguradoras globais.

1989

PostgreSQL / POSTGRES (Michael Stonebraker, UC Berkeley)

O professor Michael Stonebraker inicia o projeto POSTGRES na Universidade de Berkeley como sucessor do Ingres, priorizando extensibilidade de tipos, herança de tabelas e rigor matemático. Em 1996, ganha suporte a SQL nativo e torna-se open-source.

1995

MySQL (Michael "Monty" Widenius, MySQL AB)

Criado na Suécia pela MySQL AB, o MySQL foi projetado com foco em leveza, facilidade de uso e velocidade extrema de leitura. Tornou-se o coração da pilha LAMP (Linux, Apache, MySQL, PHP) e impulsionou a expansão da Web comercial.

2010

Era NoSQL (MongoDB, Redis, Cassandra)

Com a explosão de Big Data, redes sociais e streaming, surgem bancos não-relacionais focados em esquemas flexíveis (documentos), chave-valor em memória e alta vazão de escrita distribuída em clusters massivos.

2012

Era NewSQL (CockroachDB, Google Spanner)

Combinação do melhor dos dois mundos: bancos de dados distribuídos globalmente com escalabilidade horizontal infinita (estilo NoSQL), mas mantendo a semântica SQL tradicional e garantias estritas de transação ACID.

Hoje

Cloud Databases & Serverless (PlanetScale, Neon, Supabase)

A arquitetura moderna desacopla computação de armazenamento. Bancos como Neon (Postgres Serverless), PlanetScale (Vitess/MySQL) e Supabase oferecem autoscaling instantâneo, branching de banco como no Git e integração nativa com IA (pgvector).

MySQL vs PostgreSQL

Dois gigantes de código aberto com arquiteturas e propostas complementares para a engenharia de software.

🐬

MySQL

Velocidade & Web Clássica

O SGBD relacional mais popular da web. Focado em simplicidade, throughput altíssimo em operações de leitura e facilidade de operação em escala.

  • ✓ Motor de Armazenamento Pluggable: InnoDB (padrão transacional ACID com row-level locking) e MyISAM.
  • ✓ Replicação Primário-Réplica Madura: Replicação binária assíncrona/semissíncrona simples de configurar e operar.
  • ✓ Ecossistema Web Consolidado: Padrão oficial de CMSs como WordPress, Drupal, Magento e plataformas como Shopify, Uber e Meta.
  • ✓ Desempenho Otimizado: Baixo consumo de memória por conexão e cache de buffers extremamente eficiente para leituras concorrentes.
Melhor aplicabilidade:

Aplicações web tradicionais, blogs, lojas de e-commerce padrão, microserviços orientados a leitura e arquiteturas com replicação horizontal.

🐘

PostgreSQL

ACID Avançado & Extensibilidade

O banco de dados relacional de código aberto mais avançado do mundo. Focado em conformidade estrita com padrões SQL, integridade e poder computacional interno.

  • ✓ ACID & Concorrência MVCC: Isolamento transacional rigoroso sem lock em leituras, com suporte a Serializable Snapshot Isolation (SSI).
  • ✓ JSONB & NoSQL Nativo: Indexação de atributos JSON com operadores de consulta ultra-rápidos via índices GIN e GiST.
  • ✓ Ecossistema de Extensões: PostGIS (dados geoespaciais), TimescaleDB (séries temporais), Citus (sharding distribuído) e pgvector (IA/vetores).
  • ✓ Consultas Complexas & Paralelismo: Suporte nativo completo a CTEs recursivas, Window Functions avançadas e particionamento declarativo.
Melhor aplicabilidade:

Sistemas financeiros/FinTechs, ERPs/CRMs corporativos, análises espaciais (GIS), inteligência artificial com embeddings vetoriais e dados mistos (SQL + JSON).

🎯 Guia de Decisão: Quando usar qual?

Escolha o SGBD certo com base nos requisitos arquiteturais do seu projeto

🐬 Escolha MySQL quando:

  • Pilha LAMP/LEMP: Seu ecossistema é baseado em PHP, WordPress, Laravel ou CMSs padrão de mercado.
  • Cargas Read-Heavy: Sua aplicação faz dezenas de milhares de leituras simples por segundo com pouca complexidade analítica.
  • Simplicidade Operacional: A equipe de operações já possui ampla experiência em replicação MySQL/MariaDB.
  • Infraestrutura Leve: Recursos de memória e CPU são limitados e você precisa de inicialização e footprint enxutos.

🐘 Escolha PostgreSQL quando:

  • Rigor Transacional & FinTech: Você lida com transações financeiras, concorrência crítica e auditoria estrita.
  • Dados Híbridos & JSONB: Precisa armazenar documentos JSON e indexar campos individuais com alta performance.
  • Inteligência Artificial & Vetores: Quer usar busca vetorial (RAG) com a extensão pgvector sem precisar de outro banco.
  • Análise Geoespacial: Precisa calcular rotas, polígonos e distâncias geográficas com a extensão PostGIS.
  • Consultas Analíticas Pesadas: Utiliza CTEs avançadas, Window Functions complexas e processamento paralelo de queries.

Conceitos Fundamentais de Banco de Dados

Entenda os pilares matemáticos, lógicos e arquiteturais que garantem a segurança e a velocidade dos dados.

O Diagrama Entidade-Relacionamento (DER) mapeia o mundo real em estruturas de tabelas (Entidades), colunas (Atributos) e vínculos (Relacionamentos: 1:1, 1:N e N:N). No caso de relacionamentos N:N (Muitos para Muitos), utiliza-se uma tabela associativa intermediária com chaves compostas.

01_modelagem_n_para_n.sql
-- Exemplo de Relacionamento N:N entre Alunos e Cursos através da tabela associativa 'matriculas'
CREATE TABLE alunos (
    id BIGSERIAL PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE cursos (
    id SERIAL PRIMARY KEY,
    titulo VARCHAR(200) NOT NULL,
    carga_horaria INT NOT NULL CHECK (carga_horaria > 0)
);

-- Tabela Associativa (Pivô) com Chave Primária Composta
CREATE TABLE matriculas (
    aluno_id BIGINT REFERENCES alunos(id) ON DELETE CASCADE,
    curso_id INT REFERENCES cursos(id) ON DELETE RESTRICT,
    data_matricula TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(20) DEFAULT 'ATIVA' CHECK (status IN ('ATIVA', 'CONCLUIDA', 'CANCELADA')),
    PRIMARY KEY (aluno_id, curso_id)
);

A Normalização é o processo formal de decompor tabelas complexas para eliminar redundâncias e evitar anomalias de inserção, atualização e exclusão:

• 1FN (Primeira Forma Normal): Valores atômicos em cada coluna (sem listas ou vetores de dados em um único campo) e existência de uma Chave Primária.
• 2FN (Segunda Forma Normal): Estar na 1FN e todos os atributos não-chave dependerem integralmente de toda a Chave Primária (não apenas de parte de uma chave composta).
• 3FN (Terceira Forma Normal): Estar na 2FN e nenhum atributo não-chave depender de outro atributo não-chave (eliminação de dependências transitivas).

02_normalizacao_3fn.sql
/* ANTES (Não normalizado - anomalias de redundância e atualização):
   pedidos_desnormalizados(pedido_id, cliente_nome, cliente_cidade, cliente_estado, produto_nome, preco)
*/

-- DEPOIS (Normalizado em 3FN): Cada fato é armazenado em exatamente um lugar
CREATE TABLE cidades (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    uf CHAR(2) NOT NULL
);

CREATE TABLE clientes (
    id BIGSERIAL PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    cidade_id INT NOT NULL REFERENCES cidades(id)
);

CREATE TABLE pedidos (
    id BIGSERIAL PRIMARY KEY,
    cliente_id BIGINT NOT NULL REFERENCES clientes(id),
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

A integridade referencial garante que relacionamentos entre tabelas permaneçam válidos e consistentes em todo o ciclo de vida da aplicação. Ações como ON DELETE CASCADE propagam a exclusão e ON DELETE RESTRICT protegem registros pais contra exclusão acidental quando existem registros filhos associados.

03_chaves_e_constraints.sql
CREATE TABLE departamentos (
    id SERIAL PRIMARY KEY,
    codigo VARCHAR(10) NOT NULL UNIQUE,
    nome VARCHAR(100) NOT NULL
);

CREATE TABLE colaboradores (
    id BIGSERIAL PRIMARY KEY,
    cpf VARCHAR(14) NOT NULL UNIQUE,
    nome VARCHAR(150) NOT NULL,
    salario NUMERIC(10, 2) NOT NULL CHECK (salario >= 1412.00),
    -- FK que proíbe excluir um departamento se houver funcionários nele vinculados
    departamento_id INT NOT NULL,
    CONSTRAINT fk_colab_depto 
        FOREIGN KEY (departamento_id) 
        REFERENCES departamentos(id) 
        ON DELETE RESTRICT 
        ON UPDATE CASCADE
);

O acrônimo ACID define as garantias transacionais de um SGBD:

• Atomicidade (Atomicity): A transação é "tudo ou nada". Se qualquer operação falhar, tudo é desfeito via ROLLBACK.
• Consistência (Consistency): Transições entre estados válidos preservando todas as constraints e regras de integridade.
• Isolamento (Isolation): Transações concorrentes não interferem entre si (controlado por níveis como Read Committed e Serializable).
• Durabilidade (Durability): Uma vez confirmado com COMMIT, os dados persistem em disco mesmo em caso de queda de energia (via Write-Ahead Logging / WAL).

04_transacao_bancaria_acid.sql
-- Transferência bancária atômica entre duas contas
BEGIN TRANSACTION;

-- 1. Debita R$ 500,00 da conta de origem (bloqueia linha com FOR UPDATE)
UPDATE contas
SET saldo = saldo - 500.00
WHERE id = 101 AND saldo >= 500.00;

-- 2. Credita R$ 500,00 na conta de destino
UPDATE contas
SET saldo = saldo + 500.00
WHERE id = 202;

-- 3. Registra o log no extrato contábil
INSERT INTO extratos (conta_origem_id, conta_destino_id, valor, tipo)
VALUES (101, 202, 500.00, 'PIX_TRANSFERENCIA');

-- Se tudo ocorreu perfeitamente, confirma as alterações permanentemente:
COMMIT;

-- Caso ocorra qualquer erro de saldo insuficiente ou timeout:
-- ROLLBACK;

O índice B-Tree (Balanced Tree) é a estrutura de dados padrão para aceleração de buscas em tempo logarítmico O(log N). Ele substitui um custoso Seq Scan (varredura completa de tabela) por um veloz Index Scan. O comando EXPLAIN ANALYZE exibe o plano de execução real do otimizador de consultas.

05_indices_e_explain.sql
-- 1. Criação de índice composto para busca frequente por cliente e data
CREATE INDEX idx_pedidos_cliente_data 
ON pedidos (cliente_id, data_pedido DESC);

-- 2. Criação de índice parcial (filtra apenas pedidos pendentes, economizando espaço em disco)
CREATE INDEX idx_pedidos_pendentes 
ON pedidos (id) 
WHERE status = 'PENDENTE';

-- 3. Inspecionando o plano de execução real da query
EXPLAIN ANALYZE
SELECT id, valor_total
FROM pedidos
WHERE cliente_id = 4821
  AND data_pedido >= '2024-01-01'
ORDER BY data_pedido DESC;

Para suportar milhões de requisições sem indisponibilidade, sistemas corporativos utilizam Replicação Primário-Réplica (onde escritas vão para o nó Primário e leituras são distribuídas entre Réplicas de Leitura) aliadas a Connection Poolers (como PgBouncer ou ProxySQL) que reaproveitam conexões TCP e evitam exaustão de threads.

06_monitor_replicacao.sql
-- [PostgreSQL] Consulta de status de replicação streaming e cálculo de atraso (Lag)
SELECT 
    client_addr AS replica_ip,
    application_name,
    state,
    sync_state,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_lag,
    reply_time - write_time AS tempo_latencia
FROM pg_stat_replication;

-- [MySQL] Consulta equivalente de status de réplica
-- SHOW REPLICA STATUS\G;

Exemplos Práticos de Produção

Código SQL realista e pronto para arquiteturas empresariais de alto desempenho.

Modelagem relacional completa (DDL) para um e-commerce moderno: chaves primárias, estrangeiras com integridade referencial, constraints de checagem, tipos otimizados e índices estratégicos.

01_schema_ecommerce_producao.sql
-- ====================================================================
-- SCHEMA DE E-COMMERCE DE ALTA PERFORMANCE (POSTGRESQL / MYSQL INNODB)
-- ====================================================================

-- 1. TABELA DE CATEGORIAS
CREATE TABLE categorias (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    slug VARCHAR(120) NOT NULL UNIQUE,
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    criado_em TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. TABELA DE PRODUTOS
CREATE TABLE produtos (
    id BIGSERIAL PRIMARY KEY,
    categoria_id INT NOT NULL REFERENCES categorias(id) ON DELETE RESTRICT,
    sku VARCHAR(50) NOT NULL UNIQUE,
    nome VARCHAR(255) NOT NULL,
    descricao TEXT,
    preco NUMERIC(12, 2) NOT NULL CHECK (preco >= 0.00),
    custo NUMERIC(12, 2) NOT NULL CHECK (custo >= 0.00),
    estoque INT NOT NULL DEFAULT 0 CHECK (estoque >= 0),
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    metadados JSONB DEFAULT '{}',
    atualizado_em TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 3. TABELA DE CLIENTES
CREATE TABLE clientes (
    id BIGSERIAL PRIMARY KEY,
    cpf_cnpj VARCHAR(18) NOT NULL UNIQUE,
    nome VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    telefone VARCHAR(20),
    cidade VARCHAR(100) NOT NULL,
    uf CHAR(2) NOT NULL,
    ativo BOOLEAN NOT NULL DEFAULT TRUE,
    criado_em TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 4. TABELA DE PEDIDOS
CREATE TABLE pedidos (
    id BIGSERIAL PRIMARY KEY,
    cliente_id BIGINT NOT NULL REFERENCES clientes(id) ON DELETE RESTRICT,
    data_pedido TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDENTE'
        CHECK (status IN ('PENDENTE', 'APROVADO', 'ENVIADO', 'ENTREGUE', 'CANCELADO')),
    subtotal NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
    desconto NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
    valor_total NUMERIC(12, 2) NOT NULL DEFAULT 0.00
);

-- 5. ITENS DO PEDIDO (TABELA ASSOCIATIVA N:N)
CREATE TABLE itens_pedido (
    id BIGSERIAL PRIMARY KEY,
    pedido_id BIGINT NOT NULL REFERENCES pedidos(id) ON DELETE CASCADE,
    produto_id BIGINT NOT NULL REFERENCES produtos(id) ON DELETE RESTRICT,
    quantidade INT NOT NULL CHECK (quantidade > 0),
    preco_unitario NUMERIC(12, 2) NOT NULL CHECK (preco_unitario >= 0.00),
    CONSTRAINT uk_pedido_produto UNIQUE (pedido_id, produto_id)
);

-- 6. ÍNDICES DE ALTA PERFORMANCE
CREATE INDEX idx_produtos_categoria ON produtos (categoria_id);
CREATE INDEX idx_pedidos_cliente_data ON pedidos (cliente_id, data_pedido DESC);
CREATE INDEX idx_pedidos_status ON pedidos (status);
CREATE INDEX idx_itens_pedido_produto ON itens_pedido (produto_id);

Consultas analíticas avançadas: faturamento acumulado (Running Total), ranking por categoria via DENSE_RANK(), ticket médio e comparação de períodos com LAG().

02_analytics_cte_window_functions.sql
/*
   RELATÓRIO ANALÍTICO AVANÇADO DE VENDAS
   Calcula faturamento diário, acumulado anual e variação percentual vs dia anterior
*/

WITH VendasDiarias AS (
    SELECT
        DATE_TRUNC('day', p.data_pedido)::DATE AS data_venda,
        COUNT(DISTINCT p.id) AS total_pedidos,
        SUM(p.valor_total) AS faturamento_dia
    FROM
        pedidos p
    WHERE
        p.status IN ('APROVADO', 'ENTREGUE')
        AND p.data_pedido >= '2024-01-01'
    GROUP BY
        DATE_TRUNC('day', p.data_pedido)
),
MetricasComJanela AS (
    SELECT
        data_venda,
        total_pedidos,
        faturamento_dia,
        -- Faturamento Acumulado (Running Total)
        SUM(faturamento_dia) OVER (
            ORDER BY data_venda ASC
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS faturamento_acumulado_ano,
        -- Faturamento do dia anterior para comparação
        LAG(faturamento_dia, 1) OVER (
            ORDER BY data_venda ASC
        ) AS faturamento_dia_anterior,
        -- Média móvel de 7 dias
        AVG(faturamento_dia) OVER (
            ORDER BY data_venda ASC
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS media_movel_7d
    FROM
        VendasDiarias
)
SELECT
    data_venda,
    total_pedidos,
    ROUND(faturamento_dia, 2) AS faturamento_dia,
    ROUND(faturamento_acumulado_ano, 2) AS faturamento_acumulado,
    ROUND(media_movel_7d, 2) AS media_movel_7d,
    ROUND(
        ((faturamento_dia - faturamento_dia_anterior) / NULLIF(faturamento_dia_anterior, 0)) * 100.0,
        2
    ) AS variacao_percentual_dia
FROM
    MetricasComJanela
ORDER BY
    data_venda DESC;

Automação e segurança interna no SGBD: Stored Procedure transacional de checkout de estoque e Trigger automático de auditoria para alteração de preços.

03_procedure_e_trigger_auditoria.sql
-- 1. TABELA DE LOG DE AUDITORIA DE PREÇOS
CREATE TABLE auditoria_precos (
    id BIGSERIAL PRIMARY KEY,
    produto_id BIGINT NOT NULL REFERENCES produtos(id),
    preco_antigo NUMERIC(12, 2) NOT NULL,
    preco_novo NUMERIC(12, 2) NOT NULL,
    usuario_bd VARCHAR(100) DEFAULT CURRENT_USER,
    alterado_em TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. FUNÇÃO DA TRIGGER (PL/PGSQL)
CREATE OR REPLACE FUNCTION trg_fn_auditar_preco_produto()
RETURNS TRIGGER AS $$
BEGIN
    -- Dispara auditoria apenas quando o preço for efetivamente alterado
    IF OLD.preco <> NEW.preco THEN
        INSERT INTO auditoria_precos (produto_id, preco_antigo, preco_novo)
        VALUES (OLD.id, OLD.preco, NEW.preco);
        
        NEW.atualizado_em = CURRENT_TIMESTAMP;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 3. ASSOCIAÇÃO DA TRIGGER NA TABELA PRODUTOS
CREATE TRIGGER trg_produtos_auditoria_preco
BEFORE UPDATE ON produtos
FOR EACH ROW
EXECUTE FUNCTION trg_fn_auditar_preco_produto();

-- 4. STORED PROCEDURE PARA BAIXA CONTROLADA DE ESTOQUE
CREATE OR REPLACE PROCEDURE sp_baixar_estoque_pedido(
    p_pedido_id BIGINT
)
LANGUAGE plpgsql
AS $$
DECLARE
    item RECORD;
BEGIN
    -- Itera sobre os itens do pedido com trava FOR UPDATE
    FOR item IN 
        SELECT produto_id, quantidade 
        FROM itens_pedido 
        WHERE pedido_id = p_pedido_id
    LOOP
        -- Atualiza estoque checando disponibilidade
        UPDATE produtos
        SET estoque = estoque - item.quantidade
        WHERE id = item.produto_id AND estoque >= item.quantidade;

        IF NOT FOUND THEN
            RAISE EXCEPTION 'Estoque insuficiente para o produto ID %', item.produto_id;
        END IF;
    END LOOP;

    -- Atualiza status do pedido para APROVADO
    UPDATE pedidos SET status = 'APROVADO' WHERE id = p_pedido_id;
END;
$$;

Ferramentas & Clientes SQL

Os principais softwares utilizados por desenvolvedores e DBAs para gerenciar, consultar e otimizar bancos de dados.

🐘

pgAdmin

A ferramenta gráfica oficial e mais completa para administração do PostgreSQL. Inclui visualizador gráfico de planos de execução, monitoramento de sessões, editor de queries e gerenciamento de backup.

🦫

DBeaver

Cliente SQL universal de código aberto baseado em Java. Suporta mais de 100 bancos relacionais e NoSQL (PostgreSQL, MySQL, Oracle, SQL Server, SQLite), com gerador de diagramas ER integrado.

⚡

TablePlus

Aplicativo nativo moderno, ultra-rápido e leve para macOS, Windows e Linux. Possui interface minimalista, suporte a múltiplos tabs, edição inline de dados e atalhos de teclado ágeis.

🐬

MySQL Workbench

A IDE oficial desenvolvida pela Oracle para o MySQL. Destaca-se pela capacidade avançada de modelagem visual ER, engenharia reversa de bancos e painéis de administração de instâncias.

🚀

DataGrip (JetBrains)

A IDE profissional mais poderosa do mercado para desenvolvedores e DBAs. Oferece autocompletion com reconhecimento de esquema, refatoração de código SQL, inspeções e controle de versão.

🐝

Beekeeper Studio

Cliente SQL moderno, elegante e de código aberto com forte compromisso com a privacidade. Interface limpa, suporte a túnel SSH e visualização simplificada de tabelas e consultas.
